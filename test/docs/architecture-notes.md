## 1. What this harness is

Every node is a real `multichaind` process with its own datadir, its own P2P port and
its own RPC port. Nothing is simulated.

> **This section describes the harness as it was when these notes were written**, when
> the only regime was the native one and network behaviour was out of scope. A second
> regime was added later, and the emulation lives behind
> [`bootstrap/fabric/`](../bootstrap/fabric/); see
> [`core-fabric.md`](core-fabric.md) and [`../config/schema.md`](../config/schema.md) §6.
> What follows is still exactly true of a `native` profile, which remains the baseline
> every emulated run is compared against.

In the native regime there is **no network emulation**: no netem, no jitter, no link
delay, no namespaces.

That is the design, not a shortcut. It isolates the *protocol* — weight computation,
weighted selection, VRF/RANDAO, inter-epoch feedback, malus — from every network
variable, so a change in an observed quantity has exactly one candidate explanation.

### Consequence for the timer-race test

Because a native run has no emulated latency, the propagation term of the inversion bound
(`S1`, topology) is **negligible by construction** in that regime. Only `S2` — the
standard deviation of the scheduler residual — is a real source, and it is the primary
one there. `stat/timer_race.py` reports `S1` as measured-but-structurally-near-zero and
does not pretend otherwise. A *native* run therefore cannot refute or confirm a
latency-driven inversion claim; it can only characterise the scheduler. That claim is
exactly what a `core` profile exists to put a number on, and it is why the statistics
below were left untouched when the second regime arrived: the same test, given a run
with real propagation in it, reports a real `S1`.

## 3. THE OPEN QUESTION: the initial weight

> **Question.** With `-enablewpoa=1 -enableweightengine=1`, the `-weight=<n>` flag is
> read, validated and logged but never published — publication happens only with the
> engine *disabled*, via `ThreadRegisterNodeWeight`. So where does a node's initial
> weight of `1` come from? Does the engine define an epoch-0/1 default, or must every
> node self-publish an initial record on `wpoa-weights` before the engine takes over?

### 3.1 Answer

**Neither. There is no initial-weight mechanism at all, and none is needed.**

The `1` is not a grant and not a default. It is the **positivity floor of
`WeightEngine::ToIntegerWeight`**, which clamps the published integer to
`[1, UINT32_MAX]`:

```cpp
// src/weight_engine/weight_engine.h:344-356
static uint32_t ToIntegerWeight(double weight, double scale)
{
    double s = weight * scale;
    if (!(s >= 1.0))                       // catches NaN, negatives and s < 1
    {
        return 1;
    }
    ...
}
```

The comment above it states the intent verbatim: *"the floor of 1 enforces the
positivity invariant of the stream and of Efraimidis-Spirakis even for a degenerate
zero-activity cluster (W_k = 0)"*.

A cluster whose miner has no certified ESG score computes `esg_miner = 0`, hence
`W_k = ESG * (tau + sum c_i) = 0`, hence `w_k = 0`, hence the published integer is
exactly `1`. That is the observed "initial weight 1".

The phrase *"w_k = W_k by construction"* in the RPC layer refers to something else: it
is the **base case of the recursion** at epoch 1, where no `rho^(e-1)` feedback term
exists yet (`FinalWeight`, `weight_engine.h:321-331`). It is not a bootstrap value.

### 3.2 What actually gates a node's first weight

Two gates, both in `ThreadWeightEngine` (`src/weight_engine/weight_engine.cpp:327-476`):

1. **The node must head a cluster.** `ComputeLocalWeightForEpoch`
   (`weight_engine.cpp:306-321`) returns `false` when the local address is not a key of
   the cluster map, and the cluster map is built *only* from confirmed
   `weight-engine-membership` records: `mc_BuildClustersFromMembership`
   (`weight_records.h:472-488`) creates a key **only** for an address that appears as
   `miner_address` in some record. A node that never called `weightregistermembership`,
   and that nobody joined, is simply absent from the map. Nothing is computed, nothing
   is published, and **no error is raised** — the failure is silent.
2. **An epoch must be buried.** `LastBuriedEpoch(height, epoch_len, 6)` returns
   `(tip - 6 + 1) / epoch_len`; below 1 the thread does nothing. The earliest epoch ever
   published is epoch **1**, first computable at height `epoch_len + 6 - 1`.

### 3.3 What a miner with no record is worth to the selector

**Nothing — it is never a candidate.** The registry map only ever contains addresses
decoded from confirmed stream items, so an absent address is not iterated at all
(`WPoASelector::SelectProposer`, `wpoa_selector.h:251-281`). Where an explicit lookup
does exist the fallback is literally `0`, and `ScoreFromEntropy64` maps weight `0` to
`+infinity`, i.e. *can never win*. Private sortition bails out the same way
(`private_sortition.cpp:225-229`).

The failure mode this produces is total: **if no node has a record when wPoA engages,
`SelectProposer` returns `""`, nobody mines, no epoch ever buries, and therefore no
weight is ever computed.** The chain stops dead. See §5.

### 3.4 Is a self-publish possible at all?

There is **no RPC** that writes `wpoa-weights` — the only writers in the tree are
`StreamWeightRegistry::PublishWeightRecord` via `RegisterLocalWeight`, called from
exactly two places (the engine thread and the static thread). No `weightpublish`, no
`weightregister`, no equivalent.

A node *can* nevertheless publish a record by hand with the generic
`publishfrom <addr> wpoa-weights <addr> '{"json":{"node_address":"<addr>","weight":N}}'`,
because `DecodeWeightRecord` accepts any confirmed, self-attested item with an integer
`weight > 0` and treats `epoch` as optional. Such a record enters the map immediately
and is later superseded by the engine's own (newest-confirmed-wins). The verifier marks
it `other-epoch`, which `mc_WeightVerdictIsInvalid` does **not** treat as invalid, so it
draws no malus.

### 3.5 Decision implemented in `bootstrap/`

**No self-publish on `wpoa-weights`. The harness relies on the engine.**

Reasons, in order of weight:

1. The purpose of this harness is to measure **the deployed engine**. Hand-publishing a
   weight would inject a value the engine did not compute, and the first epochs — the
   ones the longitudinal tests compare against the last — would measure the harness
   instead of the protocol.
2. It is unnecessary. The `setup-first-blocks` auto-adjust (§5) exists precisely to
   guarantee the engine's first record confirms *before* wPoA governs, and the harness
   verifies that it did rather than assuming it.
3. It would pollute the verification channel: every hand-written record shows up as
   `other-epoch` in `weightverifyweights`, which is exactly the signal the consistency
   checks in `phase3` use to detect a genuine problem.

**What the harness does instead**, in `bootstrap/bootstrap_network.py`:

| Step | Why it is load-bearing |
|---|---|
| The admin **explicitly creates** `wpoa-weights`, `weight-engine-membership` and `weight-engine-esg` as closed streams. | The node's auto-create is one-shot per process (`weight_reader.cpp:81` sets `create_attempted = true` *before* the `try` and never clears it) and was **observed to fail in this repository** — see §8.3. |
| Every miner calls `weightregistermembership <own-address>`. | The *only* thing that puts a miner into the cluster map. Without it that miner never receives a weight, ever, and the silence is total. |
| Every company calls `weightregistermembership <its-miner-address>`. | Populates `C_k` so that `sum c_i > 0` and the clusters differ from one another. Companies are distributed over miners by the seeded RNG. |
| Every CA certifies every miner and company with `weightsetesg`. | Without an ESG score `esg_miner = 0`, so `W_k = 0` and **every** cluster publishes exactly `1`. The sortition would then be uniform, and the headline weight-vs-election test would be measuring nothing. |
| The bootstrap then **blocks** until `getallweights` reports at least one validator with a non-zero weight, and fails loudly if the tip reaches `setup-first-blocks` first. | Turns the silent deadlock of §3.3 into a diagnosed, non-zero exit. |

### 4.3 THE TRAP: `enable-wpoa` in `params.dat` does nothing

`AppInit2` reads **only** the per-phase keys. It never calls
`GetInt64Param("enablewpoa")`. The master switch expands into the six per-phase keys
**only** when it arrives on the `multichain-util create` command line.

This was not a theoretical concern — it is the first thing that broke during
exploration (§8.2). The harness therefore writes **every per-phase key explicitly**
into `params.dat` *and* passes `-enablewpoa=1 -enableweightengine=1` on every
`multichaind` command line, as the brief mandates. The two are consistent, so no
fork warning is emitted.

Note also that the master does **not** turn on `enable-weight-engine`: it expands to
weights, selection, vrf, randao, sortition and malus, and nothing else.

| Flag | Scope | Note |

| `-maxtxfee=<n>` | local wallet policy | **Mandatory, see §6.3.** |
| `-wpoadebug` | local | Verbose tracing. Off by default, switchable from the profile. |

### 4.5 Standard MultiChain parameters this harness sets

`target-block-time`, `setup-first-blocks`, `mining-diversity`, `mine-empty-rounds`,
`initial-block-reward`, `first-block-reward`, `minimum-relay-fee`,
`anyone-can-connect`. Rationale for the non-obvious ones is in §6.

**`mining-diversity` deserves a warning.** It is binding even under wPoA: with the
stock `0.3` and 4 miners the round-robin spacing is 1 block, and the observed
distribution collapses onto round robin regardless of what the weights say. The
profiles ship `mining-diversity = 0` so that the election being measured is the
weighted one.

## 5. Epoch geometry and the bootstrap race

Epochs are **block-height based**, never wall-clock:

```
epoch(height)               = height / weight-epoch-length        (1-based; epoch 0 is a "nothing buried" sentinel)
last_buried_epoch(tip, len) = (tip - 6 + 1) / len
height_of_buried_epoch(e)   = e * len + 6 - 1
```

`6` is `MC_WEIGHT_DEFAULT_STABILITY_MARGIN` — a compile-time constant, **not** a chain
parameter, so it cannot be configured and the harness hardcodes it to match the binary.
`3` is `MC_WEIGHT_SETUP_PUBLISH_MARGIN`, used only in the floor below.

### 5.1 `setup-first-blocks` is rewritten at genesis

`mc_MultichainParams::AdjustSetupFirstBlocks` raises `setup-first-blocks` to

```
floor = weight-epoch-length + 6 - 1 + 3 + 1  =  weight-epoch-length + 9
```

whenever the configured value is lower, writing the corrected value into `params.dat`
**before the hash is taken**. A larger configured value is left alone.

The harness therefore **re-reads the effective value from `getblockchainparams` after
the chain is up** and records that, rather than trusting what it wrote. Not doing so
silently shortens the measurement window.

### 5.2 The floor covers epoch geometry, not wall-clock bootstrap

The floor guarantees the engine's first record *can* confirm before wPoA governs. It
cannot know how long starting N daemons, granting permissions and confirming membership
actually takes, and past a handful of nodes that is the larger of the two. The chain
then reaches `setup-first-blocks` with an empty registry, wPoA elects nobody, and the
chain stops — the deadlock of §3.3.

`config_loader.py` therefore derives a bootstrap budget from the node count and the
block time and raises `setup-first-blocks` above the protocol floor accordingly.
Overshooting only wastes blocks; undershooting kills the run.

> **Aggiornamento post-fix (2026-09-17, branch `fix/wpoa-cpp-bugs-and-harness-simplification`).**
> The *deadlock* described above can no longer happen (A.3): while the registry has never
> carried a positive weight the node mines under the native MultiChain rules and lets wPoA
> activate by itself, so reaching `setup-first-blocks` early is no longer fatal. The
> derived budget is **kept** anyway, for a different reason: a run whose first epochs are
> spent under native mining measures round robin, not weighted sortition, and those epochs
> are then excluded from the analysis. The budget buys measurable epochs, not liveness.
> See [`fixes-changelog.md`](fixes-changelog.md) §A.3.

## 6. The economic model

Implemented to thesis §4.2.1 / §4.3.1 and Def. 6.6-6.10. Four rules, each load-bearing,
each re-derived from the code during exploration.

### 6.1 GAS is premined

`first-block-reward > 0` and `initial-block-reward = 0`. The thesis is explicit that the
currency is issued up front *"senza alcun meccanismo di conio incrementale legato alla
produzione dei blocchi"*, so a per-block subsidy is not the model. A premine alone
yields a fully spendable native currency.

This matters more than it looks. `src/weight_engine/README.md` warns that MultiChain
defaults `initial-block-reward = 0` and that **on a chain with no native currency at
all, `R_k`, the credits and the debits are all 0 and the restitution-rate feedback is
inert**. `rho` would be pinned, `w_k = W_k` forever, and the single endogenous feedback
channel of the WeightEngine — the thing the lag-1 Spearman test exists to detect —
would be untestable. The premine is what keeps it alive.

### 6.2 Who may pay whom

| Flow | Allowed | Effect |
|---|---|---|
| admin → node (seed, refuel) | yes | funds fees; **not** a reconciliation |
| miner → treasury (restitution) | yes | **the only flow that produces `R_k`** |
| company → stream (informative tx) | yes | pays a fee, transfers nothing; drives `tau` |
| company → treasury | **no** | credits a key no cluster reads; would pin `rho` for everybody |
| node → node (horizontal GAS) | **no** | not in the model |

The actor matters absolutely: the engine reads `r_e[miner_address]` and nothing else. A
company paying the treasury leaves `R_k = 0` for every cluster while looking like
activity. The harness generates only the allowed flows *and* the consistency checks in
`phase3` assert the absence of the forbidden ones over the recorded data.

The treasury is a **dedicated address, never the admin's**: with the admin as treasury a
refuel's own change output pays the treasury, and only a guard inside
`mc_AccumulateReconciliation` spares it. That guard is correct, but a harness whose job
is to demonstrate the direction rule must not depend on it.

### 6.3 The fee, and the wallet ceiling that silently blocks publishing

The thesis states a flat 0.2 GAS per transaction. MultiChain has no such parameter:
`minimum-relay-fee` is charged **per 1000 bytes**. The profiles set 0.2 GAS/KB and the
harness **records the measured fee** from the size distribution the run actually
produced, rather than assuming the per-transaction cost.

Raising the relay fee alone is not enough. The wallet has its own ceiling,
`maxTxFee = 0.1 * COIN`, and `nFeeNeeded` is capped at it — so once
`minimum-relay-fee * nBytes/1000` exceeds `maxtxfee`, the cap guarantees the very
comparison that then rejects the transaction:

```
error code: -6   Transaction too large for fee policy
```

At 0.2 GAS per 1000 bytes that is **every transaction above 500 bytes**, which is most
stream publishes — so `send` keeps working while `publish` dies, and the network looks
healthy while no record is ever written. `-maxtxfee` is wallet policy, not consensus: it
belongs on the command line, may differ per node, and changes no chain parameter. The
harness derives it from the configured fee (`fee_per_kb * 10`) so the two cannot drift.

### 6.4 `tau` does not count mining

`tau` counts confirmed transactions whose inputs the address **signed**. A coinbase has
no resolvable input signer, so **producing blocks does not raise a miner's `tau`**. A
miner that only mines, with no ESG score, sits at published weight exactly `1` forever.
This is why miners self-register membership *and* are certified, and why the profiles
give miners a restitution budget: those transactions are their only activity.

## 7. Streams, permissions and who creates what

| Stream | Open? | Created by the harness | Who writes |
|---|---|---|---|
| `wpoa-weights` | closed | **admin, explicitly** | the engine, on every node (via `wpoa-weights.write`) |
| `weight-engine-membership` | closed | **admin, explicitly** | every node, self-attested |
| `weight-engine-esg` | closed | **admin, explicitly** | CA nodes only |
| `wpoa-weights-malus` | open | node, automatically | any node |
| the informative stream (name from the profile) | closed | **admin, explicitly** | company nodes only |

The informative stream is deliberately **not** one of the weight-engine streams:
publishing test payloads onto `weight-engine-membership` would feed the engine's own
input with noise and make `tau` indistinguishable from a malformed-record test. It is
**closed**, so writing needs an explicit per-stream grant — an open stream would let any
node with `send` publish, making the informative traffic indistinguishable from anything
else and quietly permitting a role that is supposed to generate no activity to generate
some.

### 7.1 Grants issued by the admin

| Role | Permissions |
|---|---|
| all | `connect,send,receive` + `weight-engine-membership.write` + `wpoa-weights.write` |
| miners | additionally `mine` |
| CAs | additionally `high1` **and** `weight-engine-esg.write` |
| companies | additionally `<informative-stream>.write` |

`high1` is `MC_WEIGHT_CA_PERMISSION_NAME` (`src/weight_engine/weight_authorization.h:70`).
**Being a global administrator is not sufficient to call `weightsetesg`**: the admin
confers the role and does not hold it automatically. That is deliberate — it keeps "who
administers the network" distinguishable on chain from "who certifies ESG scores".

`wpoa-weights.write` is granted to **every** node, not only miners. It is safe because
records are self-attested and independently recomputable, and it costs nothing for a
node that never heads a cluster. Granting it narrowly would break the moment a company
were promoted to cluster head.

Each grant is issued as **one call per entity permission**: MultiChain rejects
comma-joined entity keys such as `a.write,b.write`.

## 8. Facts verified on a live node

`src/`, not inferred.

### 8.3 Stream auto-creation is unreliable

A single admin node was then started with the full per-phase set and left to mine for
75 s (36 blocks at `target-block-time = 2`). `liststreams` reported:

```
root
weight-engine-esg
```

**`wpoa-weights` and `weight-engine-membership` were never created**, and
`getallweights` returned `{"validators": 0, "total": 0, "weights": {}}`. The auto-create
is one-shot per process and does not retry. This is the empirical justification for the
harness creating all three streams explicitly from the admin before anything else
happens.
> **Aggiornamento post-fix (2026-09-17, branch `fix/wpoa-cpp-bugs-and-harness-simplification`).**
> Fixed at source (A.2): the three registries now share one bounded-retry state
> machine that latches only on a real broadcast. Verified — all four streams now
> appear unaided. The harness keeps creating them explicitly, but for a different
> reason: it grants per-stream permissions in the next step, and an entity
> permission cannot precede its entity. See
> [`fixes-changelog.md`](fixes-changelog.md) §A.2.


### 8.4 The premine works, and the effective setup phase is re-readable

`getinfo` reported `balance: 1000000` from `first-block-reward = 100000000000000`, and
`getblockchainparams` echoed `setup-first-blocks: 40` (the configured value, left alone
because it exceeded the floor of `20 + 9 = 29`) together with `enable-wpoa: true`,
`enable-weight-engine: true` and `weight-epoch-length: 20`.

### 8.5 The Python environment inside the container

Python 3.10.12, `numpy` 1.21.5, `pandas` 1.3.5, `scipy` 1.8.0, `matplotlib` 3.5.1,
`PyYAML` 5.4.1. **`requests` is not installed**, and the image has no apt lists to
install it from.

The brief asks for an ad-hoc JSON-RPC client built on `requests`. `rpc_client.py`
therefore uses `requests` **when it is importable** and otherwise falls back to
`urllib.request` from the standard library, behind one identical interface. Both do the
same thing — HTTP POST with `Content-Type: application/json` and HTTP Basic Auth — so
the fallback changes no behaviour, and `pip install requests` in the image silently
activates the preferred path. No third-party *RPC* library is used either way, which is
the constraint that actually matters.

The statistical modules do **not** use `scipy` even though it is present: every test is
written from its closed form, as the brief requires.

### 8.6 A joining node exits on its first run

Started against the seed with `anyone-can-connect = false`, a peer fetches the chain
parameters, creates its wallet, prints

```
Please ask blockchain admin ... to let you connect and/or transact:
multichain-cli <chain> grant <ADDRESS> connect
```

and **exits**. It does not become a daemon and never opens an RPC port. This is the
documented sequence (`Create-Blockchain.md` §5), and it means the address has to be read
from that output — there is nothing to ask over RPC until the node has been granted
`connect` and started a second time. The harness therefore runs **join → grant → launch**.

An earlier version launched and then granted, and every peer failed with *"Couldn't
connect to the seed node"* while the orchestrator waited for RPC ports that were never
going to open.

### 8.7 A restart races the LevelDB lock

Stopping the admin and restarting it immediately produced:

```
ERROR: Couldn't initialize permission database for blockchain <chain>.
       Probably multichaind for this blockchain is already running. Exiting...
IO error: lock .../permissions.db/LOCK: Resource temporarily unavailable
```

The RPC port closes before LevelDB releases its lock, so a restart inside that window
lands on a held lock and leaves a node that looks started and is not — with the seed down,
every joining peer then fails. Worse, MultiChain did **not** write a pid file here, so an
implementation that waits on the pid has nothing to wait on and returns immediately.

The fix is to treat the **RPC port** as the liveness signal: stop, poll until the port
closes, settle for two seconds, and retry a launch that reports a held lock.
> **Aggiornamento post-fix (2026-09-17, branch `fix/wpoa-cpp-bugs-and-harness-simplification`).**
> **Correction (A.7): the claim that MultiChain writes no pid file was wrong.** It
> writes `<datadir>/<chain>/multichain.pid` (`src/core/init.cpp:1111`) and removes
> it on a clean shutdown; the original check was made after the daemons had
> exited. The RPC port remains the primary signal by choice — a pid file cannot
> say whether LevelDB has released its lock, and survives a crash — with the pid
> used to escalate to a signal. See [`fixes-changelog.md`](fixes-changelog.md) §A.7.


### 8.8 An entity permission cannot be granted before its entity exists

`grant <addr> wpoa-weights.write` issued before the stream is created fails with

```
-708 Entity with this name not found: wpoa-weights
```

On the first full run this silently lost every stream permission, and the first visible
symptom was `weightregistermembership` failing with `-704 ... lacks write permission`
several steps later — by which point the cause was three phases back. Grants are therefore
issued in two passes: global permissions before the peers launch, per-stream permissions
after the streams are created.
> **Aggiornamento post-fix (2026-09-17, branch `fix/wpoa-cpp-bugs-and-harness-simplification`).**
> Reviewed and deliberately not changed (A.4): the ordering is ordinary MultiChain
> behaviour and `-708` is accurate. Improving the message would mean editing text
> that other tools parse. Documented instead in `docs/weight-engine.md` §5bis.
> The two-pass grant stays. See [`fixes-changelog.md`](fixes-changelog.md) §A.4.


### 8.9 The treasury's `receive` grant must confirm before the admin restarts

The treasury address is created on the admin, granted `receive`, and then the admin is
restarted to install `-weighttreasuryaddress`. If the grant has not been mined by then it
dies with the node, and every miner restitution afterwards fails with

```
-704 Destination address doesn't have receive permission
```

Observed on a live run: 96 consecutive failures, no restitution recorded, `R_k = 0` for
every cluster — and therefore a perfectly flat `rho` that reads as *"the feedback channel
is inert"* rather than as a broken permission. The harness now waits for the grant to
confirm, re-asserts it after the restart, and **verifies** it with `listpermissions`
before any traffic starts.
> **Aggiornamento post-fix (2026-09-17, branch `fix/wpoa-cpp-bugs-and-harness-simplification`).**
> Partly fixed at source (A.5): the node now warns at startup when the configured
> treasury lacks a confirmed `receive`. The parameter stays hash-enforced and is
> deliberately not made runtime-settable — `R_k` is defined as the value paid to
> that address, so differing values fork the chain. The harness keeps its
> confirm-and-verify as the fast-failing first line. See
> [`fixes-changelog.md`](fixes-changelog.md) §A.5.


### 8.10 The audit RPCs must exist in the binary

Run against a `src/multichaind` built twelve hours before the commit that added them,
every round- and epoch-audit family answered `-32601 Method not found`:
`wpoalistscores`, `wpoalistdelays`, `wpoalisteffectiveweights`, `wpoalistfinalweights`,
and the whole `weightlist*` / `weightgetlocal*` set. Phase 1 collected 750 errors and
produced empty tables — a pipeline that ran to completion and measured nothing.

`./docker/mcsim run mc-build` fixes it. The check is cheap:

```bash
strings src/multichaind | grep -c '^wpoalistfinalweights$'
```

### 8.11 The delay formula reproduces exactly

With the rebuilt binary, `wpoalistdelays` reported for one validator
`score_norm = 0.99999999991224` and `delay = 2.99999999982448` at
`target_block_time = 2`, `delta = 0.5`, `lambda = 0`. Recomputing

```
D = T + delta*T*(2*score_norm - 1) + lambda*Phi
  = 2 + 0.5*2*(2*0.99999999991224 - 1) + 0
  = 2.99999999982448
```

reproduces it to the last digit, and across a whole run
`delay_recompute_mismatch_rounds = 0`. That is the pass condition of the functional test:
the harness and the node agree about the mechanism, so the timer-race results downstream
are about the chain rather than about a misunderstanding.

### 8.12 The binaries only run inside the container

`src/multichaind` on the host fails with `libboost_filesystem.so.1.74.0: cannot open
shared object file`. Ubuntu 22.04 with Boost 1.74 is supplied by `./docker/mcsim`, per
the project's standing rule. Every entry point of this harness is written to run inside
that container.

## 9. Decisions taken

| # | Decision | Reason |
|---|---|---|
| 1 | No self-publish on `wpoa-weights`; rely on the engine's own floor and publication. | §3.5. Measuring the engine is the point. |
| 2 | Admin explicitly creates all three weight streams plus the informative stream. | §8.3 — auto-create was observed to fail. |
| 3 | Every per-phase wPoA key written into `params.dat`, and `-enablewpoa=1 -enableweightengine=1` on every command line. | §4.3 / §8.2, plus the brief's hard requirement. |
| 4 | Miners self-register membership; companies register to a miner chosen by the seeded RNG. | §3.2 — the only path into the cluster map. |
| 5 | Every miner and company receives an ESG score from a CA. | §3.5 — without it every cluster publishes `1` and the election is uniform. |
| 6 | Treasury is a dedicated address created on the admin and passed to every node as `-weighttreasuryaddress`. | §6.2. Set uniformly on all nodes, so the hash-enforced value never differs. |
| 7 | `mining-diversity = 0` in every profile. | §4.5 — otherwise round-robin spacing masks the weighted election. |
| 8 | `-maxtxfee` derived as `fee_per_kb * 10`. | §6.3 — otherwise publishing fails silently. |
| 9 | `setup-first-blocks` derived from the node count, then re-read from the chain. | §5.1–§5.2. |
| 10 | One OS process per daemon, launched with `subprocess`, each with its own `.jsonl`. | The brief: daemons must stay individually killable and individually diagnosable. |
| 11 | `requests` preferred, `urllib` fallback. | §8.5. |
| 12 | Experiment seed and analysis seed are **separate**. `seed` in the profile drives the network and the traffic; the phase-3 tests use a fixed `20260905` independent of it. | The brief. It keeps a re-run with a different network seed comparable under the identical test procedure. |
| 13 | Peers are brought up **join → grant → launch**, not launch-then-grant. | §8.6 — a joining node exits on its first run and has no RPC port to be asked on. |
| 14 | A stop waits on the **RPC port closing**, not on a pid file, and a launch retries a held lock. | §8.7 — MultiChain did not write a pid file, and the lock outlives the port. |
| 15 | Grants are issued in two passes, global then per-stream. | §8.8 — an entity permission before its entity is `-708`, and the symptom surfaces three steps later. |
| 16 | The treasury's `receive` is confirmed, re-asserted after the restart, and verified. | §8.9 — otherwise `R_k = 0` everywhere and the feedback looks inert rather than broken. |
| 17 | `wpoa-weights-malus` is created explicitly, **open**, matching the node's own creation. | Its auto-creation is as unreliable as the others', and the failure is only visible as a missing stream in the logs. |
| 18 | The first and last epoch of each daemon are marked `full_epoch = False` and excluded from the range check. | Both are partial by construction — the first began before the daemon started, the last was cut short by the shutdown — so their counts cannot be expected to fall in the configured range. |
